# Звіт до лабораторної роботи № 1

## 1. Тема, номер і варіант

- Тема: розгортання Java-проєкту та базова обробка даних.
- Лабораторна робота № 1, варіант 15 – «Доставлення посилок».
- Операційна система: Windows 11 Pro, Eclipse Temurin JDK 21.0.12; у CI – Ubuntu, Windows і macOS.
- Репозиторій: https://github.com/dxom9kl/kzp-lab01-kost
- Стан лабораторної роботи № 1: тег `v1.0.0` – https://github.com/dxom9kl/kzp-lab01-kost/tree/v1.0.0

## 2. Мета роботи

Пройти повний шлях від створення репозиторію до консольної програми, яку відтворено
збирають і запускають на Windows, macOS та Ubuntu.

Досягнуто рівня 3 «повний цикл»:

- Maven-проєкт із Maven Wrapper, JUnit 5, SpotBugs і виконуваним jar;
- GitHub Actions перевіряє кожну зміну на трьох ОС і публікує jar як артефакт;
- версія записана лише в `pom.xml` і тезі `v1.0.0`, а `--version` виводить її з номером збірки CI;
- програма читає записи про доставлення посилок, відкидає хибні рядки з поясненням,
  обчислює чотири показники та записує однаковий звіт у консоль і файл;
- роботу сплановано й здано через GitHub Issues і Pull Request, дефекти пов'язано з
  виправленнями через `Closes #N`.

## 3. Постановка задачі

Формат запису: `id:String; weightKg:double; city:String; deliveryDays:int; express:boolean`.

Показники:

1. Кількість коректних записів.
2. Середня вага посилки.
3. Найбільший термін доставлення (разом з ідентифікатором і містом посилки).
4. Кількість експрес-доставлень.

Правила перевірки рядка (причиною пропуску стає перша знайдена проблема):

| Перевірка | Повідомлення |
|---|---|
| рядок порожній або з самих пробілів | `порожній рядок` |
| кількість полів не 5 | `очікується 5 полів, отримано N` |
| порожнє текстове чи числове поле | `порожній ідентифікатор посилки`, `порожня вага`, `порожнє місто`, `порожній термін доставлення`, `порожня ознака експрес-доставлення` |
| вага не відповідає `-?\d+(\.\d+)?` (`важка`, `2,50`, `NaN`, `1e3`, `10d`, пробіли, `+2`) | `вага не є числом: "…"` |
| вага з сотень цифр, що дає `Infinity` | `вага завелика` |
| вага `<= 0` | `вага має бути додатною: …` |
| термін не відповідає `-?\d+` (`2.5`, `два`, пробіли, `+2`) | `термін доставлення не є цілим числом: "…"` |
| термін не вміщується в `int` | `термін доставлення завеликий: "…"` |
| термін `< 0` | `від'ємний термін доставлення: …` |
| `express` не `true` і не `false` (`так`, `TRUE`, `1`) | `ознака експрес-доставлення має бути true або false: "…"` |
| `id` уже траплявся в коректному записі | `повторний ідентифікатор посилки … (уперше в рядку N)` |

Термін `0` допустимий (доставлення в день відправлення), нульова вага – ні.
`Boolean.parseBoolean` не використовується для перевірки, бо мовчки повертає `false`
для будь-якого тексту.

## 4. Структура програми

| Файл | Відповідальність |
|---|---|
| `Main.java` | точка входу: викликає парсер аргументів, запускає контролер, повертає код завершення |
| `cli/ArgumentsParser.java` | розбір `--input`, `--output`, `--help`, `--version`; текст довідки |
| `cli/Arguments.java` | record із режимом роботи та шляхами до файлів |
| `cli/UsageException.java` | помилка в аргументах (код завершення 2) |
| `DeliveryController.java` | керує обробкою: читання файла, перевірка рядків, повторні `id`, показники, звіт |
| `delivery/ParcelParser.java` | розбір і перевірка одного рядка, індекси полів |
| `delivery/InvalidRecordException.java` | причина пропуску рядка |
| `delivery/DeliverySummary.java` | накопичення чотирьох показників |
| `report/ReportFormatter.java` | текст звіту з `Locale.ROOT` і `%n` |
| `report/FileReport.java` | читання та запис файлів у UTF-8 через `Path`, видалення BOM |
| `BuildInfo.java` | версія з `pom.xml` і номер збірки з `version.properties` |
| `ExitCode.java` | коди завершення: 0 – успіх, 1 – помилка даних, 2 – помилка аргументів |

Потік даних:

```text
args → ArgumentsParser.parse → Arguments
     → DeliveryController.run → FileReport.readLines
     → для кожного рядка ParcelParser.parse
         коректний і з новим id: DeliverySummary.add
         хибний або повторний:   «Рядок N: причина»
     → ReportFormatter.format → консоль + FileReport.writeReport
     → код завершення → Main → System.exit
```

`Main` не містить обробки: так радить викладач для наступних робіт, і цю архітектуру
закладено вже в першій. `main` лише передає результат `run` у `System.exit`, а `run`
приймає потоки виводу параметрами, тому його можна тестувати: `System.exit` у тесті
зупинив би JVM разом із JUnit.

Розбір аргументів, керування обробкою, перевірка, обчислення та форматування розділені
по класах, щоб у лабораторній роботі № 2 замінити масиви рядків власними класами без
зміни зовнішньої поведінки.

## 5. Інфраструктура

- **Maven**: `pom.xml` з координатами `ua.lpnu.kzp:lab01:1.0.0`, Java 21 (`maven.compiler.release`),
  UTF-8; компілятор з `-Xlint:all` і `failOnWarning` зупиняє збірку на будь-якому попередженні.
- **Maven Wrapper** 3.3.4 (Maven 3.9.11): `mvnw`, `mvnw.cmd`, `.mvn/wrapper/`. У `.gitattributes`
  для `mvnw` задано LF, для `*.cmd` – CRLF; `mvnw` має в Git право на виконання.
- **Залежності**: JUnit Jupiter 5.12.2 зі `scope test`.
- **Статичний аналіз**: SpotBugs 4.9.7.0, ціль `check` у фазі `verify`, найсуворіші налаштування
  (`effort Max`, `threshold Low`).
- **Пакування**: maven-shade-plugin 3.6.0, `Main-Class: ua.lpnu.kzp.Main`,
  без `dependency-reduced-pom.xml` у корені проєкту.
- **Версія**: `version.properties` заповнюється Maven (resource filtering) значеннями
  `${project.version}` і `${build.number}`; `BuildInfo` читає цей ресурс.
- **CI** (`.github/workflows/ci.yml`): матриця `ubuntu-latest`, `windows-latest`, `macos-latest`;
  JDK 21 Temurin; кеш Maven; `clean verify` з `-Dbuild.number=${{ github.run_number }}`;
  перевірка виводу `--version` (для тегу `v*` – збіг із назвою тегу); запуск jar на
  `data/input.csv`; публікація артефакта `lab01-<os>-build-<N>`. Запускається на Pull Request,
  push у `main` і теги `v*`.
- **Шаблони**: форми Issues `feature.yml`, `bug.yml` і `PULL_REQUEST_TEMPLATE.md`.

### Версія коду та номер CI-збірки

Версію продукту записано в одному місці – `pom.xml`. У програму вона потрапляє
автоматично під час збірки: Maven копіює `src/main/resources/version.properties` у
`target/classes` і підставляє замість шаблонів значення з POM. У коді немає жодної
константи з версією, тож забути її оновити неможливо.

Версія `1.0.0` описує стан коду за правилами SemVer (MAJOR.MINOR.PATCH) і змінюється
лише разом із продуктом. Номер збірки (`github.run_number`) – порядковий номер запуску
workflow: той самий код можна зібрати багато разів, і кожна збірка отримає новий номер.
SemVer відокремлює метадані збірки знаком `+`, тому `1.0.0+41` і `1.0.0+42` – одна версія.

```text
$ java -jar target/lab01-1.0.0.jar --version     # локальна збірка
1.0.0+local

$ java -jar lab01-1.0.0.jar --version            # jar з артефакта CI № 6
1.0.0+6
```

## 10. Академічна доброчесність

Під час роботи використано Claude Code (Anthropic, модель Claude Opus 5.5) у застосунку
Claude для Windows. Викладач на занятті дозволив використовувати ШІ на власний розсуд.

**Ролі-агенти:** описані в каталозі `ai/` – Менеджер, DevOps, Розробник, Валідатор,
Документатор, Рецензент (роль, вміння, обмеження, промпт).

**Внесок ШІ:**

- аналіз методичних вказівок і план роботи на рівень 3;
- установлення Git, GitHub CLI, VS Code і Maven, налаштування Git;
- `pom.xml`, Maven Wrapper, `.gitignore`, `.gitattributes`, `.editorconfig`;

## 11. Відповіді на контрольні питання

1. **Яке призначення файла pom.xml?**
   `pom.xml` описує проєкт для Maven: координати артефакта (`groupId`, `artifactId`, `version`),
   версію Java, кодування, залежності та плагіни, прив'язані до фаз збірки. Завдяки йому
   проєкт збирається однією командою на будь-якому комп'ютері. У нашому проєкті це ще й
   єдине місце, де записано версію продукту.

2. **Чим відрізняються фази test, verify і package у Maven?**
   Фази виконуються в порядку `test` → `package` → `verify`, і виклик пізнішої виконує всі
   попередні. `test` компілює код і запускає тести, `package` збирає jar, а `verify` перевіряє
   вже зібраний результат – у нас там працює SpotBugs. Тому один `verify` у CI і тестує,
   і пакує, і перевіряє проєкт, а jar після нього вже лежить у `target/`.

3. **Навіщо потрібен Maven Wrapper?**
   Скрипти `mvnw`, `mvnw.cmd` і файл `.mvn/wrapper/maven-wrapper.properties` під час першого
   запуску завантажують точно визначену версію Maven (3.9.11). Тож проєкт однаково
   збирається в будь-кого й у CI без установленого Maven. JDK Wrapper не замінює.

4. **Яку роль відіграє метод main?**
   `main` – точка входу, з якої JVM починає виконання; через `String[] args` він отримує
   аргументи командного рядка. У нашій програмі `main` лише викликає `run` і передає код
   завершення в `System.exit`, а розбір аргументів і обробку виконують `ArgumentsParser`
   і `DeliveryController`.

5. **Чим примітивний тип відрізняється від String?**
   Змінна примітивного типу (`int`, `double`, `boolean`) зберігає саме значення, не може бути
   `null` і не має методів. `String` – посилальний тип: змінна зберігає посилання на
   незмінний об'єкт із методами (`split`, `isBlank`, `formatted`), може бути `null`, а
   порівнювати рядки треба через `equals`, а не `==`.

6. **Чому середнє потрібно обчислювати в double, навіть якщо сума й кількість мають тип int?**
   Ділення двох `int` цілочислове й відкидає дробову частину: `7 / 2 = 3`. Якщо один операнд
   має тип `double`, ділення стає дробовим: `(double) 7 / 2 = 3.5`. У нас сума ваги –
   `double`, тому `totalWeightKg / count` дає точне середнє.

7. **Що станеться, якщо Integer.parseInt отримати рядок "abc"?**
   Метод кине `NumberFormatException`; без перехоплення програма аварійно завершиться.
   У нашій програмі формат перевіряється регулярним виразом ще до перетворення, і рядок
   пропускається з причиною `термін доставлення не є цілим числом: "abc"`. Виняток можливий
   лише при переповненні `int`, і його теж перехоплено.

8. **Чому не можна мовчки пропускати рядок із помилкою?**
   Користувач не дізнається, що частину даних відкинуто, і вважатиме показники повними.
   Тому кожен пропущений рядок потрапляє у звіт із номером і причиною – дані можна знайти й
   виправити.

9. **Як String.split(";", -1) обробляє порожнє останнє поле?**
   Від'ємний ліміт зберігає порожні поля наприкінці: `"UA-1;1.00;Київ;2;"` дає 5 полів, останнє
   порожнє, і програма повідомляє `порожня ознака експрес-доставлення`. Без `-1` метод відкинув
   би порожній хвіст і повернув 4 поля, тож причина була б неправильною.

10. **Чому для шляхів краще використовувати Path.of, а не "data\\input.csv"?**
    Роздільник шляху в Windows – `\`, а в macOS і Ubuntu – `/`. `Path.of("data", "input.csv")`
    сам підставляє правильний роздільник, а рядок `"data\\input.csv"` на Linux означав би
    файл, у назві якого є зворотна коса риска.

11. **Навіщо явно задавати StandardCharsets.UTF_8?**
    Кодування за замовчуванням залежить від ОС і налаштувань JVM, і українські літери в
    іншому кодуванні перетворюються на незрозумілі символи. Явне UTF-8 дає однаковий
    результат на всіх трьох ОС, а файл в іншому кодуванні програма відхиляє з повідомленням.

12. **Чим %n відрізняється від \n у форматованому виводі?**
    `\n` – завжди символ LF. `%n` підставляє роздільник рядків поточної ОС: CRLF у Windows і
    LF у macOS та Ubuntu. SpotBugs навіть попереджає про `\n` у форматних рядках.

13. **Які дані потрібно перевірити у вашому варіанті?**
    Порожній рядок і кількість полів (5); непорожні `id`, вага, місто, термін і `express`;
    вага – скінченне десяткове число з крапкою, більше нуля; термін – ціле число від нуля в
    межах `int`; `express` – рівно `true` або `false`; унікальність `id`; BOM на початку файла.

14. **Які тести виявлять помилку в обчисленні середнього?**
    `DeliverySummaryTest.averageWeightKeepsFraction` (1.00, 2.00 і 2.50 дають 5.5 / 3 –
    виявить цілочислове ділення), `emptySummaryHasZeroMetrics` (порожній набір не ділить на
    нуль), `MainTest.processesSampleData` (8 записів дають 6.45 кг, звірено вручну) і випадки
    з `NaN` у `ParcelParserTest`, які не пускають `NaN` у суму.

15. **Яке призначення статичного аналізатора?**
    SpotBugs аналізує байт-код без запуску програми й шукає типові дефекти: незакриті потоки,
    можливий `null`, залежність від кодування за замовчуванням, `\n` у форматних рядках тощо.
    Він працює у фазі `verify`, тож проєкт із попередженнями не збереться ні локально, ні в CI.

16. **Яку роль виконує GitHub Actions?**
    Для кожного Pull Request і push у `main` автоматично запускає однакову збірку на трьох ОС:
    компіляцію, тести, SpotBugs, пакування і запуск jar. Так виявляються помилки, яких не
    видно на одному комп'ютері (права на `mvnw`, кінці рядків, шляхи), а зібраний jar
    публікується як артефакт.

17. **Чим версія програми відрізняється від номера збірки CI і чому їх розділяє знак +, а не крапка?**
    Версія `1.0.0` описує стан коду й змінюється в `pom.xml` разом із кодом. Номер збірки – це
    номер запуску workflow, новий навіть для того самого коду. За SemVer усе після `+` – метадані
    збірки, які не змінюють версію: `1.0.0+41` і `1.0.0+42` – одна версія. Запис `1.0.0.42`
    читався б як інша, чотиричислова версія.

18. **Що має містити GitHub Issue на дефект?**
    Заголовок, кроки відтворення (команду та вхідні дані), очікуваний і фактичний результат;
    за потреби – версію програми й ОС. Форма `bug.yml` вимагає ці поля; приклади – #12–#14.

19. **Що Ви повинні вказати у розділі звіту про академічну доброчесність?**
    Який інструмент і яку модель ШІ використано, які ролі-агенти і з якими промптами, що
    зробив ШІ, а що – я, які рекомендації прийнято, які помилки знайдено й виправлено, і
    підтвердити, що результати правдиві, а весь поданий код я розумію.

20. **Яку роботу виконує агент DevOps, а яку – агент Валідатор?**
    DevOps відповідає за інфраструктуру: `pom.xml`, Maven Wrapper, SpotBugs, пакування jar,
    GitHub Actions і діагностику помилок збірки. Валідатор шукає крайові випадки, не
    виправляючи код: складає хибні вхідні дані, звіряє показники з ручним обчисленням і
    оформлює дефекти як Issues – так з'явилися #12–#14.

21. **Який рядок вашої програми найскладніше пояснити і чому?**
    `Pattern.compile("-?\\d+(\\.\\d+)?")` у `ParcelParser`. Треба пояснити сам регулярний вираз
    (необов'язковий мінус, цифри, необов'язкова дробова частина), подвійні зворотні риски в
    рядку Java і те, навіщо ця перевірка взагалі потрібна: `Double.parseDouble` сам по собі
    приймає `NaN`, `1e3`, `10d` і пробіли.

## 12. Висновки

Створено першу версію консольного продукту «Доставлення посилок»: програма читає записи з
UTF-8 файла, відкидає хибні дані з номером рядка й причиною, обчислює чотири показники та
формує однаковий звіт у консоль і файл. Проєкт збирається однією командою через Maven
Wrapper, перевіряється тестами та SpotBugs і автоматично збирається на Windows, macOS та
Ubuntu з публікацією jar. Версія задана лише в `pom.xml` і підставляється в програму під час
збірки.

У лабораторній роботі № 2 масиви рядків (`String[]` з індексами `ParcelParser.ID` тощо)
буде замінено власним класом посилки: `ParcelParser` повертатиме об'єкт замість масиву,
а `DeliverySummary` прийматиме його без повторного перетворення чисел. Класи `Main`,
`ArgumentsParser`, `DeliveryController`, `ReportFormatter` і `FileReport` збережуть своє
призначення.
