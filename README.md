# Доставлення посилок: консольний звіт

[![CI](https://github.com/dxom9kl/kzp-lab01-kost/actions/workflows/ci.yml/badge.svg)](https://github.com/dxom9kl/kzp-lab01-kost/actions/workflows/ci.yml)

Лабораторні роботи № 1–4 з курсу «Кросплатформні засоби програмування», варіант 15.

Програма читає записи про доставлення посилок із CSV-файла, перевіряє кожен рядок,
обчислює чотири показники й записує однаковий звіт у консоль і текстовий файл.
Хибні рядки не зупиняють роботу: у звіті вказано номер рядка та причину пропуску.

Поточний стан відповідає ЛР № 4: колекцію посилок обробляють запити Stream API, а зовнішня поведінка
лишилася такою, як у попередніх роботах. Звіти: [ЛР № 4](REPORT.md), [ЛР № 3](reports/lab03.md),
[ЛР № 2](reports/lab02.md), [ЛР № 1](reports/lab01.md).

## Формат входу

Файл у кодуванні UTF-8, один запис у рядку, поля розділено крапкою з комою,
рядка заголовка немає:

```text
id;weightKg;city;deliveryDays;express
```

| Поле | Тип | Правило |
|---|---|---|
| `id` | String | непорожній і унікальний у файлі |
| `weightKg` | double | число з крапкою (`2.50`), більше нуля |
| `city` | String | непорожнє, можна з українськими літерами, апострофом і дефісом |
| `deliveryDays` | int | ціле число, не менше нуля (`0` – доставлення в день відправлення) |
| `express` | boolean | лише `true` або `false` |

Порожні рядки, неправильна кількість полів, нечислові значення (`важка`, `2,50`, `NaN`,
`1e3`, пробіли навколо числа) і від'ємні числа відкидаються з поясненням.
Приклад даних – [`data/input.csv`](data/input.csv): 8 коректних і 21 хибний рядок.

## Показники

1. Кількість коректних записів.
2. Середня вага посилки, кг.
3. Найбільший термін доставлення разом з ідентифікатором і містом посилки.
4. Кількість експрес-доставлень.

## Модель даних

Кожен коректний рядок стає незмінним об'єктом одного з підтипів абстрактного класу
[`Parcel`](src/main/java/ua/lpnu/kzp/delivery/Parcel.java). Підтип обирає фабрика
`Parcel.fromCsv(line)` за полем `express`, а решта програми працює зі спільним типом.

```text
                Parcel (abstract)
     id, weightKg, city, deliveryDays
     getKind(), calculatedDays(), calculatedCost()
                 ▲               ▲
     RegularParcel               ExpressParcel
     reserveDays                 acceleratedDays
```

| Підтип | `DeliveryKind` | Розрахунковий термін | Вартість |
|---|---|---|---|
| `RegularParcel` | `REGULAR` | плановий термін + резерв днів | базовий тариф |
| `ExpressParcel` | `EXPRESS` | плановий термін − дні прискорення | базовий тариф × 1.5 + 25 грн за день прискорення |

Базовий тариф становить 40 грн + 10 грн за кілограм. Усі тарифи демонстраційні. Вхідний файл не містить
резерву чи прискорення, тому в посилок із файла ці поля нульові, а розрахунковий термін дорівнює плановому.

Базовий тип перевіряє спільні інваріанти, тому хибний об'єкт неможливо створити:

| Поле | Інваріант | Причина відхилення |
|---|---|---|
| `id` | не `null` і не порожній | `порожній ідентифікатор посилки` |
| `weightKg` | скінченне число, більше нуля | `вага має бути додатною`, `вага завелика`, `вага не є числом` |
| `city` | не `null` і не порожнє | `порожнє місто` |
| `deliveryDays` | не менше нуля | `від'ємний термін доставлення` |
| `reserveDays` (`RegularParcel`) | не менше нуля, сума з терміном вміщується в `int` | `від'ємний резерв днів`, `резерв днів завеликий` |
| `acceleratedDays` (`ExpressParcel`) | від нуля до планового терміну | `від'ємне прискорення доставлення`, `прискорення … перевищує плановий термін` |

Посилки рівні, якщо мають однаковий підтип, однакові спільні поля й однакове власне поле підтипу.
`equals` і `hashCode` узгоджені, тому посилки можна зберігати в `HashSet` і використовувати як ключі `HashMap`.

Спадкування обрано, бо звичайна й експрес-посилка є різновидами посилки та мають спільний стан і правила.
Абстрактний клас, на відміну від інтерфейсу, зберігає ці поля в одному місці. `DeliverySummary` лише
використовує посилки, тому він пов'язаний із ними композицією.

Record [`WeightDelivery`](src/main/java/ua/lpnu/kzp/delivery/WeightDelivery.java) зберігає
проміжний підсумок: кількість посилок, сумарну вагу й найбільший термін. Метод `plus(Parcel)`
повертає новий підсумок і не змінює попередній.

## Потокові запити

Клас [`ParcelQueries`](src/main/java/ua/lpnu/kzp/delivery/ParcelQueries.java) містить запити варіанта.
Кожен запит створює власний потік і не змінює вхідний список.

| Запит | Метод | Операції | Результат |
|---|---|---|---|
| Посилки в дорозі | `inTransit` | `filter`, `toList` | `List<Parcel>` |
| Міста | `cities` | `map`, `toList` | `List<String>` |
| Кількість за містом | `countByCity` | `groupingBy`, `counting` | `Map<String, Long>` |
| Статистика ваги | `weightStatistics` | `summarizingDouble` | `DoubleSummaryStatistics` |
| Найважчі посилки | `topByWeight` | `sorted`, `limit`, `toList` | `List<Parcel>` |
| Пошук за номером | `findById` | `filter`, `findFirst` | `Optional<Parcel>` |

- **Статус.** Вхідний файл не містить статусу, тому enum `DeliveryStatus` визначає його за контрольним другим
  днем: посилка з розрахунковим терміном понад 2 дні `у дорозі`, решта `доставлено`.
- **Групування.** `TreeMap` упорядковує міста за кодами Unicode, тому порядок не залежить від вхідного файла.
- **Top-5.** Вага впорядковується за спаданням, а однакову вагу розрізняє номер за зростанням. `sorted` виконується
  до `limit`. `N = 0` дає порожній результат, завеликий `N` повертає всі посилки, а від'ємний відхиляється.
- **Пошук.** За дубльованого номера повертається перший запис, а за відсутнього – `Optional.empty()`.
- **Показники звіту.** `DeliverySummary` обчислює їх потоковими запитами. Середня вага лишається послідовною сумою
  (`reduce`), бо `summarizingDouble` використовує компенсоване підсумовування й може округлити результат інакше.

Відмінності від ЛР № 3:

| Частина | ЛР № 3 | ЛР № 4 |
|---|---|---|
| Показники | накопичення в полях `DeliverySummary` | потокові запити `ParcelQueries` |
| Сума, кількість, найбільший термін | `totals.plus(parcel)` для кожної посилки | `reduce` з `WeightDelivery::plus` |
| Посилка з найбільшим терміном | умова в методі `add` | `reduce` із вибором першої найбільшої |
| Кількість за видами | `EnumMap.merge` у методі `add` | `groupingBy` з `EnumMap` |
| Перелік пропущених рядків | цикл `for` | `map` і `Collectors.joining` |
| CSV, показники, текст звіту | – | без змін |

## Збірка

Потрібен JDK 21. Maven установлювати не треба: Maven Wrapper сам завантажить версію,
указану в `.mvn/wrapper/maven-wrapper.properties`.

```text
mvnw.cmd clean verify        # Windows
./mvnw clean verify          # macOS, Ubuntu
```

`verify` компілює код, запускає тести, збирає виконуваний jar і перевіряє байт-код SpotBugs.

## Запуск

```text
java -jar target/lab01-1.3.0.jar
java -jar target/lab01-1.3.0.jar --input data/input.csv --output out/report.txt
java -jar target/lab01-1.3.0.jar --help
java -jar target/lab01-1.3.0.jar --version
```

| Аргумент | Призначення | За замовчуванням |
|---|---|---|
| `--input <файл>` | вхідний CSV-файл | `data/input.csv` |
| `--output <файл>` | файл звіту | `out/report.txt` |
| `--help` | довідка | |
| `--version` | версія з `pom.xml` і номер збірки | |

Коди завершення: `0` – успіх; `1` – файл не знайдено, не прочитано чи не записано або в
ньому немає жодного коректного запису; `2` – помилка в аргументах.

У консолі Windows перед запуском виконайте `chcp 65001`, інакше частина українських
літер може вивестися як `?`. Файл звіту завжди записується в UTF-8.

## Версія

Версію продукту записано лише в `pom.xml`. Під час збірки Maven підставляє її у
`version.properties`, а `--version` додає номер збірки: `1.3.0+local` для локальної
збірки і `1.3.0+<N>` у CI, де `N` – номер запуску GitHub Actions. Стан лабораторних робіт
позначено Git-тегами: № 1 – `v1.0.0`, № 2 – `v1.1.0`, № 3 – `v1.2.0`, № 4 – `v1.3.0`.

## CI

[GitHub Actions](.github/workflows/ci.yml) на кожен Pull Request, push у `main` і тег `v*`
запускає `verify` на `ubuntu-latest`, `windows-latest` і `macos-latest`, перевіряє вивід
`--version`, запускає jar на `data/input.csv` і публікує jar як артефакт
`lab01-<ОС>-build-<N>`.
