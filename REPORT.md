# Звіт до лабораторної роботи № 1

## 1. Тема, номер і варіант

- Тема: розгортання Java-проєкту та базова обробка даних.
- Лабораторна робота № 1, варіант 15 – «Доставлення посилок».
- Операційна система: Windows 11 Pro, Eclipse Temurin JDK 21.0.12 (код компілюється з `--release 21`).
- Репозиторій: https://github.com/dxom9kl/kzp-lab01-kost
- Стан лабораторної роботи № 1: тег `v1.0.0` – https://github.com/dxom9kl/kzp-lab01-kost/tree/v1.0.0

Назва репозиторію містить номер роботи та прізвище, як вимагають методичні вказівки.
Стан, поданий на перевірку, зафіксовано Git-тегом `v1.0.0`.

## 2. Мета роботи

Пройти шлях від порожнього репозиторію до консольної програми, яку однаково збирають і
запускають на Windows, macOS та Ubuntu.

Досягнуто:

- Maven-проєкт із Maven Wrapper, JUnit 5, SpotBugs і виконуваним jar;
- GitHub Actions збирає й тестує проєкт на трьох ОС і публікує jar як артефакт;
- програма читає записи про доставлення посилок, пропускає хибні рядки з поясненням,
  обчислює чотири показники та записує звіт у консоль і файл;
- роботу сплановано й здано через GitHub Issues та Pull Request.

## 3. Постановка задачі

Формат запису: `id:String; weightKg:double; city:String; deliveryDays:int; express:boolean`.

Показники:

1. Кількість коректних записів.
2. Середня вага посилки.
3. Найбільший термін доставлення.
4. Кількість експрес-доставлень.

Правила перевірки рядка (причиною пропуску стає перша знайдена проблема):

| Перевірка | Повідомлення |
|---|---|
| рядок порожній або з самих пробілів | `порожній рядок` |
| кількість полів не 5 | `очікується 5 полів, отримано N` |
| порожній ідентифікатор або місто | `порожній ідентифікатор посилки`, `порожнє місто` |
| порожня вага, термін або ознака | `порожня вага`, `порожній термін доставлення`, `порожня ознака експрес-доставлення` |
| `weightKg` не відповідає `-?\d+(\.\d+)?` (`важка`, `2,50`, `NaN`, `1e3`, `10d`, пробіли) | `вага не є числом` |
| `weightKg` із сотень цифр, що дає `Infinity` | `вага завелика` |
| `weightKg <= 0` | `вага має бути додатною` |
| `deliveryDays` не відповідає `-?\d+` (`2.5`, `два`, `+2`, пробіли) | `термін доставлення не є цілим числом` |
| `deliveryDays` не вміщується в `int` | `термін доставлення завеликий` |
| `deliveryDays < 0` | `від'ємний термін доставлення` |
| `express` не `true` і не `false` (`так`, `TRUE`, `1`) | `ознака експрес-доставлення має бути true або false` |
| `id` уже був у коректному записі | `повторний ідентифікатор посилки` |

Нульовий термін допустимий (доставлення в день відправлення), нульова вага – ні.

## 4. Структура програми

| Файл | Відповідальність |
|---|---|
| `Main.java` | запуск парсера аргументів і контролера, код завершення |
| `cli/ArgumentsParser.java` | розбір `--help`, `--version`, `--input`, `--output` |
| `DeliveryController.java` | керування обробкою: читання файла, перевірка рядків, показники, звіт |
| `delivery/ParcelParser.java` | розбір і перевірка одного рядка |
| `delivery/DeliverySummary.java` | накопичення чотирьох показників |
| `report/ReportFormatter.java` | формування тексту звіту з `Locale.ROOT` |
| `report/FileReport.java` | читання та запис файлів у UTF-8 через `Path` |
| `BuildInfo.java`, `version.properties` | версія з `pom.xml` і номер CI-збірки для `--version` |

Допоміжні типи: `Arguments` (розібрані аргументи), `UsageException` і `InvalidRecordException`
(причини помилок), `ExitCode` (коди завершення 0, 1, 2).

Потік даних:

```text
args → ArgumentsParser.parse → DeliveryController.run → FileReport.readLines
     → для кожного рядка ParcelParser.parse
     → коректний: DeliverySummary.add / хибний або повторний: «Рядок N: причина»
     → ReportFormatter.format → консоль + FileReport.writeReport
```

`main` нічого не обробляє сам: він викликає `run`, а той розбирає аргументи й запускає
контролер. Код завершення `run` повертає, а `main` передає його в `System.exit`, тож `run`
можна перевіряти тестами без зупинки JVM.

Розбір аргументів, перевірка, обчислення й форматування живуть в окремих класах, тому в
лабораторній роботі № 2 масиви рядків можна замінити власним класом посилки, не змінюючи
поведінки програми.

## 5. Інфраструктура

- **Maven**: `pom.xml` з координатами `ua.lpnu.kzp:lab01:1.0.0`, Java 21, UTF-8.
- **Maven Wrapper** 3.3.4 (Maven 3.9.11): `mvnw`, `mvnw.cmd`, `.mvn/wrapper/`.
  У `.gitattributes` для `mvnw` задано LF, для `*.cmd` – CRLF.
- **Залежності**: JUnit Jupiter 5.12.2 зі `scope test`.
- **Статичний аналіз**: SpotBugs 4.9.7.0, ціль `check` у фазі `verify`.
- **Пакування**: maven-shade-plugin 3.6.0, `Main-Class: ua.lpnu.kzp.Main`.
- **Версія**: Maven фільтрує `version.properties` і підставляє `${project.version}` та
  `${build.number}`.
- **CI** (`.github/workflows/ci.yml`): матриця `ubuntu-latest`, `windows-latest`,
  `macos-latest`; JDK 21 Temurin; кеш Maven; `clean verify` з
  `-Dbuild.number=${{ github.run_number }}`; запуск зібраного jar з `--version` і на
  `data/input.csv`; публікація артефакта `lab01-<os>-build-<N>`.
- **Шаблони**: форми Issues `feature.yml`, `bug.yml` і `PULL_REQUEST_TEMPLATE.md`.

### Версія коду та номер CI-збірки

Версію продукту записано лише в `pom.xml`. У програму вона потрапляє під час збірки
через `version.properties`, тому в коді немає константи, яку довелося б оновлювати
вручну. Версія `1.0.0` збігається з тегом `v1.0.0` і змінюється тільки разом із кодом.
Номер збірки – це номер запуску workflow; повторна збірка того самого коду отримує
новий номер. За SemVer номер збірки пишеться після `+`, тому `1.0.0+9` і `1.0.0+10` –
одна й та сама версія.

```text
$ java -jar lab01-1.0.0.jar --version
1.0.0+10
```

## 11. Відповіді на контрольні питання

1. Яке призначення файла pom.xml?\
   Описує проєкт для Maven: координати, версію Java, кодування, залежності й плагіни. Це єдине місце, де записано версію.
2. Чим відрізняються фази test, verify і package у Maven?\
   Порядок такий: test → package → verify. test запускає тести, package збирає jar, verify перевіряє зібране (у нас SpotBugs).
3. Навіщо потрібен Maven Wrapper?\
   Завантажує потрібну версію Maven (3.9.11), тож проєкт збирається будь-де без установленого Maven.
4. Яку роль відіграє метод main?\
   Це точка входу програми, яка отримує аргументи командного рядка. У нас він лише запускає `run` і повертає код завершення.
5. Чим примітивний тип відрізняється від String?\
   Примітив зберігає саме значення й не може бути `null`; `String` – об'єкт із методами, рядки порівнюють через `equals`.
6. Чому середнє потрібно обчислювати в double, навіть якщо сума й кількість мають тип int?\
   Ділення двох `int` відкидає дробову частину: `7 / 2 = 3`, а `(double) 7 / 2 = 3.5`.
7. Що станеться, якщо Integer.parseInt отримати рядок "abc"?\
   Буде `NumberFormatException`. У нас формат перевіряється раніше, і рядок пропускається з причиною.
8. Чому не можна мовчки пропускати рядок із помилкою?\
   Користувач не дізнається, що частину даних відкинуто, і вважатиме показники повними.
9. Як String.split(";", -1) обробляє порожнє останнє поле?\
   Зберігає його: `"a;b;"` дає три поля, останнє порожнє. Без `-1` воно б зникло.
10. Чому для шляхів краще використовувати Path.of, а не "data\\input.csv"?\
    `Path.of("data", "input.csv")` сам підставляє роздільник ОС (`\` у Windows, `/` в Unix).
11. Навіщо явно задавати StandardCharsets.UTF_8?\
    Кодування за замовчуванням залежить від ОС; без UTF-8 українські літери можуть зіпсуватися.
12. Чим %n відрізняється від \n у форматованому виводі?\
    `\n` – завжди LF, а `%n` – роздільник рядків поточної ОС (CRLF у Windows).
13. Які дані потрібно перевірити у вашому варіанті?\
    Кількість полів, непорожні значення, вагу (число, більше нуля), термін (ціле, не менше нуля), `express` (лише `true`/`false`), унікальність `id`.
14. Які тести виявлять помилку в обчисленні середнього?\
    `DeliverySummaryTest.averageWeightKeepsFraction` (дробове середнє), `emptySummaryHasZeroMetrics` (ділення на нуль) і `MainTest.processesSampleData` (6.45 кг).
15. Яке призначення статичного аналізатора?\
    Шукає типові помилки в байт-коді без запуску програми; збірка з попередженнями SpotBugs не проходить.
16. Яку роль виконує GitHub Actions?\
    Автоматично збирає й тестує кожну зміну на трьох ОС і публікує jar як артефакт.
17. Чим версія програми відрізняється від номера збірки CI і чому їх розділяє знак +, а не крапка?\
    Версія описує код і змінюється вручну в `pom.xml`, номер збірки росте з кожним запуском CI. За SemVer частина після `+` – лише метадані збірки, а `1.0.0.10` виглядало б як нова версія.
18. Що має містити GitHub Issue на дефект?\
    Кроки відтворення, очікуваний і фактичний результат (форма `bug.yml`).
19. Що Ви повинні вказати у розділі звіту про академічну доброчесність?\
    Інструмент ШІ, ролі, що зробив ШІ і що я, виправлені помилки та підтвердження, що я розумію поданий код.
20. Яку роботу виконує агент DevOps, а яку – агент Валідатор?\
    DevOps налаштовує Maven, SpotBugs, пакування й CI; Валідатор шукає крайові випадки й оформлює дефекти, не виправляючи код.
21. Який рядок вашої програми найскладніше пояснити і чому?\
    `Pattern.compile("-?\\d+(\\.\\d+)?")` у `ParcelParser`: треба пояснити регулярний вираз і те, чому `Double.parseDouble` без нього приймає `NaN` чи `1e3`.

## 12. Висновки

Створено першу версію консольного продукту «Доставлення посилок»: програма читає записи
з UTF-8 файла, пропускає хибні рядки з номером і причиною, обчислює чотири показники та
записує однаковий звіт у консоль і файл. Проєкт збирається однією командою через Maven
Wrapper, перевіряється тестами та SpotBugs і збирається в CI на Windows, macOS та Ubuntu
з публікацією jar.

У лабораторній роботі № 2 масиви рядків (`String[]` з індексами `ParcelParser.ID` тощо)
буде замінено власним класом посилки, а `ParcelParser` повертатиме об'єкт замість масиву.
`Main`, `ArgumentsParser`, `DeliveryController`, `ReportFormatter` і `FileReport` збережуть
своє призначення.
